Valid network values:

GET /api/v1/orders/ – List My Orders

Returns all orders placed via API.

GET /api/v1/bundles/ – List Available Bundles

Returns all active bundle packages.

GET /api/v1/balance/ – Check Wallet Balance

Returns your current wallet balance, debt balance, and debt access status.

// Request
GET /api/v1/balance/
Authorization: Bearer YOUR_TOKEN

// Response
{
  "wallet_balance": "150.00",
  "debt_balance": "0.00",
  "debt_access": false
}

wallet_balance and debt_balance are returned as strings to preserve exact decimal precision — parse them as decimals, not floats, in your integration. debt_access indicates whether your account can carry a balance below zero (debt) — if false, orders will fail if your wallet balance is insufficient.

GET /api/v1/orders-summary/ – Waiting, Refunded & Refund-Requested Orders

Returns your full waiting/refund picture in one call — orders you placed directly plus orders your customers placed through your generated links. Recommended endpoint for tracking money owed to you.

// Request
GET /api/v1/orders-summary/
Authorization: Bearer YOUR_TOKEN

// Response
{
  "waiting": {
    "count": 5,
    "total": "36.12",
    "orders": [
      {
        "order_id": "SKP41737719",
        "network": "MTN",
        "recipient": "0552387954",
        "gb_size": "5.00",
        "price_paid": "21.80",
        "amount_owed": "21.80",
        "status": "waiting",
        "created_at": "2026-07-24T20:35:55Z"
      }
    ]
  },
  "refunded": {
    "count": 0,
    "total": "0",
    "orders": []
  },
  "refund_requested": {
    "count": 0,
    "total": "0",
    "orders": []
  }
}

gb_size is the data bundle size in GB for that order. amount_owed is the amount payable to you — for orders placed through your generated links, this is your cost price, not the retail price your customer paid. refund_requested lists orders where a refund was requested; each order includes a paid field indicating whether it has been paid out yet.

GET /api/v1/status/{order_id}/ – Check Order Status

Returns the current status of a specific order.

// Request
GET /api/v1/status/SKP36648705/
Authorization: Bearer YOUR_TOKEN

// Response
{
  "order_id": "SKP36648705",
  "status": "delivered"
}

// Possible status values:
// pending    – Order received, awaiting processing
// processing – Sent to network, delivery in progress
// delivered  – Data delivered successfully
// failed     – Delivery failed

?? Delivery Notifications (Webhook)

Instead of polling for order status, register a URL on your server. We will automatically send a POST request to that URL whenever an admin marks your order as delivered.

GET /api/v1/callback/ – Get Registered Callback URL

Returns your currently registered callback URL.

// Response
{
  "callback_url": "https://yourserver.com/webhook"
}

POST /api/v1/callback/ – Register Callback URL

Register the URL on your server that should receive delivery notifications. Only needs to be done once.

// Request body
{
  "callback_url": "https://yourserver.com/your-webhook-endpoint"
}

// Success response
{
  "message": "Callback URL registered successfully.",
  "callback_url": "https://yourserver.com/your-webhook-endpoint",
  "note": "We will POST to this URL when your orders are delivered."
}

?? Every notification we send includes an X-GigMax-Signature header. Verify this on your server to confirm the request is genuinely from us.

?? Troubleshooting Failed Requests

If your integration shows a generic error (e.g. "invalid response," "order failed") but you're not sure why, check these in order:

  1. Log the raw response. Before showing any error to your users, log the exact HTTP status code and response body you received. A generic catch-all error message hides the real cause — always inspect the actual response first.
  2. Confirm the request actually reached us. If you see a network-level error (timeout, connection refused, DNS failure) in your own logs, the request never reached our server — this is a connectivity issue on your end or your host's network, not something we can debug from our side.
  3. Check your base URL. Confirm you're calling https://gigmax.com/api/v1/ exactly — typos or a stale/cached URL are a common cause of silent failures.
  4. Verify your network/gb_size values against the accepted list above — a 404 with "Bundle package not found" means one of these didn't match.
  5. Still stuck? Contact support with: the exact timestamp of the failed request, your account phone number, and the raw response (or network error) you received. Without these details we can't look up what happened on our end.
