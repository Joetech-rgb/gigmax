The GigMax API lets approved API agents place data bundle orders, check order statuses and refunds, and receive delivery updates from their own systems. Requests and responses use JSON.

Base URL

{{ base }}/api/v1/

Every endpoint works with or without a trailing slash. This page documents only what is currently implemented.

Endpoint summary

GETbundles/List active bundles with your price

GETstatus/<order_id>/Status of one order

Send your token in the Authorization header of every request:

Authorization: Bearer YOUR_TOKEN

Requests without a valid token, or from accounts without approved API access, get 401.

  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \

curl {{ base }}/api/v1/status/ORDER_ID/ \
  -H "Authorization: Bearer YOUR_TOKEN"

Use the network and gb_size values exactly as returned by bundles/.

Charges your wallet (or adds to your debt, where your account allows it) and creates the order. Requires approved API access and an account that is not paused.

Order creation is limited to 20 requests per minute per IP address. Space out bulk submissions and wait a minute before retrying if requests are rejected. On a timeout, call status/ or orders/ before retrying, so you do not buy the same bundle twice.

All require Authorization: Bearer YOUR_TOKEN and return 401 without a valid token.

Unknown order, or an order that is not yours: 404.

GET waiting/?page=1&page_size=50

Your API orders with status waiting or unverified, with total_count, total_amount, page, total_pages, has_next, has_previous and an orders list.

GET orders-summary/

Groups waiting, unverified and refund_requested, each with count, total and orders. It also includes orders placed through your generated links, and each order shows amount_owed.

StatusMeaningWhat to do
pendingOrder created, not yet sent for deliveryWait, then poll status/
processingBeing deliveredWait
deliveredDelivered to the recipientNothing
waitingHeld. No refund has been issued yetWait, or contact support
unverifiedThe contact could not be verified. A refund may follow, but none has been issued while this status showsCheck again later, or contact support
refundedThe order failed and your account was credited when refund_credited is trueNothing
failedThe order failedCheck status/, then contact support
Statuses can change after the first response. Do not treat waiting, unverified or pending as final, and use status/<order_id>/ as the source of truth when a webhook is missed.

Refunds are decided and applied by GigMax, not by an API call. When an API order is refunded, the amount reverses your debt first and any remainder is credited to your wallet. The order then shows refunded with refund_credited: true. You cannot request or trigger a refund through the API.

Register your URL

curl -X POST {{ base }}/api/v1/callback/ \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"callback_url": "https://yourserver.com/your-webhook-endpoint"}'

The URL must start with http:// or https:// (otherwise 400). Send an empty callback_url to clear it. GET callback/ shows the URL currently registered.

What we send

A POST with a JSON body when an API order changes to processing, delivered, waiting, refunded or failed. The event name is order.<status>.

{
  "event": "order.delivered",
  "order_id": "GMX12345678",
  "status": "delivered",
  "message": null,
  "recipient": "0240000000",
  "network": "MTN",
  "gb_size": "1",
  "price": "4.50",
  "timestamp": "2026-10-18T10:05:00+00:00"
}
No retries. Each event is sent once with a 10-second timeout, and failed deliveries are not retried. The unverified status is never sent by webhook. Poll status/<order_id>/ as the fallback, and make your handler safe to run twice for the same order.

Requests to GigMax are authenticated only by your Bearer token. They do not carry a signature. Always use HTTPS, keep the token on your server, and rotate it if you think it leaked.

Webhooks from GigMax carry an X-GigMax-Signature header: the hex HMAC-SHA256 of the raw request body, using your API token as the secret. Verify it before trusting the payload:

import hmac, hashlib

def is_valid(raw_body: bytes, header_value: str, api_token: str) -> bool:
    expected = hmac.new(api_token.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header_value or "")
Compute the signature over the exact bytes you received, not over re-serialized JSON. If verification suddenly fails everywhere, check whether the token was rotated, because the signing secret changes with it.

Common problems

Always getting 401. Check the header is exactly Authorization: Bearer YOUR_TOKEN, the token was not rotated, and your API access is still approved.

Duplicate order (409). The same recipient and bundle was ordered within 10 minutes. Use the returned order_id instead of resubmitting.

Order stays waiting or unverified. Poll status/<order_id>/. If it does not change, contact support with the order ID.

No webhook arrived. Webhooks are not retried, so poll status/. Confirm your URL with GET callback/ and that your server answers within 10 seconds.

Signature check fails. Use the raw body bytes, the current token as the secret, and compare the hex digest.
